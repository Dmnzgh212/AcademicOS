# Local Dashboard

## Product intent

The dashboard is not intended to look like a generic CRUD/admin panel. Its first job is to answer, at a glance:

- What is definitely happening today?
- What changed since I last checked?
- What needs my review before it changes the calendar?
- What work is due soon?
- What study time has the adaptive planner placed today?
- Is there an immediate overload/deadline risk?

## Information semantics

The UI distinguishes three important object types:

- **Confirmed / Truth** — factual academic commitments from the Truth Calendar;
- **Plan** — movable study blocks generated by the planner;
- **Candidate / Review** — evidence-backed changes not yet accepted as facts.

The distinction is expressed through labels, layout, border/shape treatment, and color rather than color alone.

## First implementation

The first dashboard deliberately avoids a frontend framework:

```text
Python ThreadingHTTPServer
  -> server-rendered HTML
  -> local CSS
  -> local SQLite
```

Reasons:

- no Node toolchain for a mostly read-only v0.1 dashboard;
- no separate frontend dev server;
- no API service required just to display local data;
- easy to package and maintain;
- almost zero runtime overhead.

If later interaction becomes complex enough to justify a richer frontend, the rendering layer can be replaced without changing the underlying Truth/Plan/Candidate models.

## Privacy defaults

The server binds to `127.0.0.1` by default and refuses a non-loopback host unless code explicitly opts into remote binding.

The page loads:

- no Google Fonts;
- no CDN JavaScript;
- no remote icon library;
- no analytics;
- no third-party assets.

Private dashboard responses use `Cache-Control: no-store` and a no-referrer policy.

## Today page

The v0.1 Today dashboard contains:

- weekly confirmed-course strip;
- four compact headline metrics;
- merged Today timeline of Truth Calendar + Plan Calendar;
- Attention/risk panel;
- Changes Inbox;
- Upcoming Work;
- Recent Activity.

It is responsive down to mobile width even though desktop is the primary AcademicOS environment.

## Morning Brief

The dashboard and CLI share the same deterministic `MorningBrief` builder. This prevents separate UI logic from inventing a different interpretation of the underlying state.

Inputs:

- effective Truth Calendar for target date;
- activity feed lookback;
- pending CandidateEvents;
- upcoming tasks;
- Plan Calendar blocks;
- deterministic deadline/workload alerts.

No LLM is required to render the daily operational view.
