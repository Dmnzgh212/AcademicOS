# LifeHub 防止过度执行：需求价值与工程比例决策标准（审计建议）

**2026-10-09 Draft；用于解释 LH-D-LOCAL-002，不取代个人主权、最小权限或实际安全审查。**

## 1. 做之前先判断是否值得做

工程复用的目标是**节省真正复杂能力的研发成本**，不是“每一个功能都必须复制一个开源项目”。每项新功能开工前用简短说明回答：

1. **真实用途：** 哪个用户/业务流程需要它，成功后如何观察价值？仅展示引擎能力的项目必须写明“测试样例”，不能伪称实用模块。
2. **简单替代：** 现有依赖、标准库或一段清楚的小函数能否解决？排序、单位格式化、简单字符串处理等优先按简单方式实现。
3. **复用价值：** 复杂文档解析、索引搜索、调度、同步、成熟协议实现等，才重点研究可合法本地化的开源实现。可选择性复制、维护本地 fork 或固定版本依赖；由许可、风险、维护/更新成本决定，而非机械“必须复制”。
4. **边界必要性：** 只有功能确需独立升级、跨模块复用、独立权限或故障隔离时才引入可安装插件/Wasm。**M1 技术测试需要两个包，不代表每项小功能必须拆成两个包。**
5. **投入与收益：** 如果简单需求竟引入新的编译器、两种语言、特设协议、独立分发链和复杂 CI，应说明确切收益；否则视为过度工程化，停止非必要增强。
6. **安全与交付：** 必须保留可信来源/许可、最小权限、撤销/卸载、故障/资源边界与适用平台的真实验证。安全关键依赖优先维护成熟组件，不能为了“复制优先”自己重写数据库、Wasm VM 或密码学。

这些不是机械的代码行数和工时指标，不为每个小函数额外增加一场审批会。可以在 PR 描述里用几行完成判断。

## 2. 五种不同的结论，不能互相替代

| 检查项 | 问的是什么 |
| --- | --- |
| **需求价值** | 有真实场景、值得长期维护吗？ |
| **工程比例** | 比标准库/简短实现有明显收益吗？ |
| **技术行为** | 代码/测试究竟运行了什么？ |
| **安全范围** | 哪些边界已验证、哪些未覆盖？ |
| **交付体验** | Windows 普通用户能否导入、运行、撤权、复制脱敏错误？ |

允许“技术行为 PASS、工程比例 FAIL”。CI 通过、许可合规、产生安装包，不能自动变成有用产品。真实故障/安全修复仍须完成，不能以“低价值”掩盖风险。

## 3. 正确区分 Engine、研究和产品

- **M1 Engine 验收：** 需要两个受控模块、guest 真正后台工作、授权通信/撤销、崩溃/恢复、Windows/Linux installed wheel 证明。这些工程样例即使很小也是正当测试；但不需外部人类开发者，且不自动构成产品。
- **业务本地化：** 值得复用的**大型复杂能力**先筛选成熟开源，再合法复制/裁剪/适配受控本地模块。小型功能直接做，不为体现“本地化”硬套两包或 Wasm。
- **普通用户：** 工程侧负责源代码/许可/安全/环境准备；用户只需导入、启动、看结果、审查撤销权限、停止/卸载、反馈脱敏错误。
- **Windows 优先：** Windows 是主要用户交付平台，Linux 继续承担引擎兼容测试；没有证据不开发两个完整桌面发行版。
- **PersonIR/WIT：** 继续研究隔离，不用研究 PR 数量推动新编译器生产。

## 4. 历史倒查后的停止点

PR #71 的自然排序确实通过18项模块测试以及 Windows/Linux CI，但目前只是 16 个 ASCII 名称的局部排序，额外的 C/Zig/Wasm/双包工程成本相对过高。PR #72 的 Windows 离线套件/中文菜单提供有限可操作性，却没有改变底层功能的低价值。**将 #71/#72 归类为测试和包装样例，暂停继续扩大排序业务范围**。保留已验证代码、许可证、回归脚本和 Windows 包装经验；无需毁掉已有成果。

PR #34 归类为三类源数据/授权接入验证，而非三款现成业务插件。PR #65 归类为后台 Engine 的合成工作量验证，而非真实能源应用。v0.1 #32/#33 仍保持限定原型接受状态。

下一款实用模块必须先通过需求/价值审查，再决定是短代码、固定依赖还是开源大模块本地化；无需一开始就搭建完整插件商店或发行系统。
