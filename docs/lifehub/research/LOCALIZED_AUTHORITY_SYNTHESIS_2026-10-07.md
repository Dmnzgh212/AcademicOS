# LifeHub 本地个人授权语义：复用研究与比较计划

日期：2026-10-07（America/Toronto）。状态：**研究提案，未执行比较实验，非生产规范**。
依据：[核心理念重申 PR #62](https://github.com/Dmnzgh212/AcademicOS/pull/62)。
PersonIR 语义研究重新开放；新源语言/编译器仍无生产准入依据。
本研究不修改 Core，不增加运行时依赖，不宣称 M1 接入门槛已经完成。

## 结论先行

LifeHub 应复用现成的执行、接口、授权与数据来源机制，把自己的研究集中在：
**个人如何委托权限；权限如何随安装、执行、撤销而失效；数据如何从观察变成推导、提案和外部效果；这些过程如何被解释和追责。**

“本土化”在这里是适配本地个人计算与真实插件生态：本机运行、个人授权根、
离线条件、跨插件组合、可换 Shell、可撤销的自动化。不是把外部方案改名后声称原创。
不能把个人生活领域的分类写进 Core，也不把个人身份当作软件可随意修改的对象。

## 一、经过核对的先例及适配边界

以下只概述原机制；右列是 LifeHub 的研究判断，不是来源已经证明的结论。

| 来源 | 原机制概要 | LifeHub 适配判断与限制 |
| --- | --- | --- |
| [WIT worlds](https://component-model.bytecodealliance.org/design/worlds.html) | 描述组件提供/需要的接口与宿主表面；不描述组件内部行为。 | 借鉴显式 imports/exports 与版本化契约。类型正确不等于授权正确、无泄露或有来源证明。生产仍用当前 core-Wasm；Component Model 保持隔离实验。 |
| [UCAN Delegation](https://github.com/ucan-wg/delegation) | 明确委托链、主体、命令、条件和时间等约束。 | 借鉴有根的委托与限制逐级收窄；不直接引入 DID、签名令牌或网络协议。本地安装/执行身份不能由 guest 自报。规范研究不等于实现成熟度评估。 |
| [UCAN Revocation](https://github.com/ucan-wg/revocation) | 撤销特定委托证明，保留不可逆撤销记录；其它有效证明链仍可能授权。分发一致性由部署承担。 | 研究“撤销某条委托”与“禁止某动作”的区别。本地权威记录可实时查询；离线设备不能凭签名声称已知所有撤销。不要照搬最终一致语义后仍承诺立即撤销。 |
| [Cedar authorization](https://docs.cedarpolicy.com/auth/authorization.html) | 围绕 principal/action/resource/context 做授权判断，默认拒绝，适用 forbid 覆盖 permit。 | 借鉴集中决策与显式拒绝。策略引擎不会替宿主发现伪造身份、过期快照或未标记的数据；暂不增加 Cedar 依赖。 |
| [W3C PROV-DM](https://www.w3.org/TR/prov-dm/) | 用 entity/activity/agent 及生成、使用、派生、关联、代理关系描述来源。 | 借鉴可交换的来源词汇；来源记录是陈述，不自动证明真实性、同意或合法性。个人、插件和宿主角色必须区分。 |
| [Jif decentralized label model](https://www.cs.cornell.edu/jif/doc/jif-3.3.0/dlm.html) | 把保密与完整性策略组合成标签，分别约束阅读者和影响者。 | 研究派生数据继承约束、授权降密与多主体数据。标签来源必须可信；完整追踪任意 guest 的控制依赖/隐式流不能靠一个 JSON 字段实现。 |

生产已使用 Wasmtime、SQLite、Python/OS 进程机制。继续使用其维护中的实现，
不新写 VM、存储引擎、加密原语或通用 RPC。以上资料不是新增依赖清单。

本轮没有复制任何上游实现。若以后采用依赖或拷贝代码，应先固定上游版本/提交、
核对该组件实际许可证与归属、审查维护和安全状态、记录修改范围与更新责任。
参考设计、采用库、复制源代码是三个独立决定；不能以文档开放推断代码许可。

## 二、把机制组织成个人授权语义

这是一份概念模型，不是 PersonIR 语法或准备落地的数据库 schema。

| 概念 | 拟表达的含义 | 当前生产事实 |
| --- | --- | --- |
| PersonalDomain | 与个人关联的数字数据/授权域，不等于对人本身的修改权限。 | trusted local operator；尚无远程、多用户身份边界。 |
| Authority | 谁授予什么动作、资源、约束和期限；撤销对象必须可识别。 | 已有能力与路由批准；完整委托链/期限模型未实现。 |
| ExecutionBinding | 此次操作属于哪个已批准安装和具体执行实例。 | package snapshot 与 live execution binding 已有测试；不是密码学发行者认证。 |
| Evidence | 某外部或本地观察的来源陈述与采集活动。 | 不能声称已有统一、可信观察模型。 |
| Derived | 从输入计算得到的结果，保留输入关系与可信度边界。 | 当前没有任意 Wasm 内部完整信息流追踪。 |
| Proposal | 对受保护持久状态的候选改变，附目标版本与相关权限。 | 已有 host-mediated proposal/commit；不证明新范式优势。 |
| EffectRequest | 候选外部动作，附接收方、披露内容、授权与来源。 | 已有 staged request；没有真实通用外部效果执行器。 |
| Commit / Effect | 权威执行的状态改变或外部动作；必须明确一致性/结果边界。 | commit 重验证已有边界；真实外部效果与不确定结果仍有限。 |

自然语言例子：用户可授权自动整理课程资料，但不能由这个授权推出“可向任意 AI
上传所有邮件”。拒绝一个日程提案，也不能抹掉已经收到的原始公告。
家庭设备操作失败或结果不明时，不能为了让状态好看而把“请求已批准”写成“已执行”。
这些领域例子属于插件/实验；Core 只认识通用机制。

拟研究的允许条件（逻辑纲要，不是已证明公式）：

```text
允许操作 = 可信宿主身份
         且 安装/执行绑定仍有效
         且 存在覆盖本动作和资源的有效委托
         且 相关拒绝/撤销没有使其失效
         且 数据披露与目标相容或有明确降密授权
         且 持久状态版本/效果阶段检查通过
```

必须分别研究每项的真实性。把它们放进一张图或一次 policy 调用，不会自动得到安全性。
预算、期限、接收者范围和用途的语义也不同：用途声明可以审计，但任意代码声称
“只用于学习”不等于宿主能证明实际用途。不能把用途文本当作隔离保证。

## 三、五种借鉴如何协同，而不是混为一谈

1. **接口层**回答“什么数据和函数能交换”；不授予交换权限。
2. **授权层**回答“此时此身份能否操作此资源”；宿主提供可信事实。
3. **来源层**回答“此结果由哪些输入和活动产生”；不能替代真实性验证。
4. **信息流层**回答“派生结果可去哪里、可影响什么”；降密/认可需相关授权。
5. **状态与效果层**回答“何时真正改变状态、外部动作是否完成”；需要事务与失败语义。

本地单一权威宿主可以先使用已有授权记录、快照重验证、显式披露与来源 metadata。
跨设备/多主体不能直接沿用“当前 SQLite 查到没撤销就安全”的假设；网络隔离、
撤销新鲜度、冲突和离线许可都需要另外定义。本轮不启动 Personal Mesh。

## 四、PersonIR 必须公平比较的基线

不要拿完整 PersonIR 对比一个故意丢掉标签、来源或检查的简单 Wasm demo。

- **B0 当前事实基线**：当前 Wasm + Capability + Contract + Host Policy +
  Proposal/Effect + 安装/执行绑定。记录真实缺口，不伪造平台已具备的功能。
- **B1 合理常规候选**：普通 Wasm/接口加统一 metadata、同样的来源与标签约束、
  同样的授权检查。它仍是研究比较对象，不代表已修改 Core。
- **R PersonIR 候选**：声明性操作图表达同样的数据、权限、来源和阶段，仍调用同样
  的可信 host 边界。不给 R 更多权限或更强的宿主实现。

如果 B1 同样阻止错误，R 只能主张表达、解释或维护的优势，不能主张独有安全性。
如果优势来自新增 host check，应将功劳归于 host check。
如果需要可信的完整数据流追踪，必须说明允许哪些操作、哪些逃逸路径及宿主漏洞。
新语言不能证明其控制范围之外的原生代码、外部系统或物理世界行为。

## 五、可证伪研究矩阵

这些是待执行的实验，不是已验证结果。使用合成数据，不调用支付、发信或设备服务。

| 场景 | 对抗动作 | 预期性质 | R 与 B1 的比较问题 |
| --- | --- | --- | --- |
| 学术观察 → 规划提案 | 拒绝提案后试图删除来源观察 | 观察不因拒绝而被改写；提案/来源可区分 | 普通 record type 与 host policy 是否已足够？ |
| 邮件摘要 → 外部 AI 请求 | 摘要丢掉输入标签，以“匿名文本”披露 | 未经授权的派生个人数据不能降密 | 谁能可信地传播标签？是否覆盖控制流依赖？ |
| 两人共享笔记 → 导出 | 只用一人的同意导出双方受限数据 | 尊重各方权限，定义冲突与最小披露 | 既有标签/策略组合能否表达？不要预设唯一解。 |
| 委托支付请求 | 读权限被解释为付款权；请求重放 | 权限不升级；请求/执行分开；不确定结果不盲重试 | capability + outbox/idempotency 是否已解决？ |
| 家庭设备命令 | 批准后、执行前撤销；执行结果丢失 | 执行前重验证；无法证明完成时报告 unknown | IR 能否超越 executor/host 的可靠性限制？ |
| 多插件分析链 | 更换安装或 provider 后复用旧授权 | 旧链不能凭新实例自动刷新权限 | 现有 package/execution binding 是否已足够？ |

每个场景保存：原始输入/期望轨迹、B0/B1/R 实际轨迹、拒绝原因、依赖的可信事实、
宿主检查数量、作者需补的手工代码、标记/检查遗漏、反例和解释质量。
没有运行实验就不填 PASS，不捏造性能或百分比。

## 六、继续/停止判据

研究应优先验证一个重复出现的实际插件问题。当前 M1 独立开发者接入仍未完成，
因此这里是候选研究问题，而不是已有生态痛点的证明。

1. 若不同领域插件没有出现共同缺口，继续记录，不能据此扩大 Core。
2. 若 B1 用普通契约与 host policy 清楚解决，保留该机制，停止“必须新语言”的论证。
3. 若 R 降低复杂度，需要保存可复现任务、同等作者条件和完整成本；不能只数图节点。
4. 若 R 只有封闭操作集内的静态性质，应明确边界，不宣称一般 Wasm 非干扰。
5. 只有重复真实需求与公平对比支持后，才提出一个独立的生产准入决定；研究成功
   不自动授权编译器开发、WIT 升级或运行时 merge。

本轮产物是机制适配表、信任边界和比较矩阵。执行实验/测量尚未进行。
已有 2026-10-03 No-Go 仍是当前编译器生产基线；语义研究重开不抹掉旧反例。
