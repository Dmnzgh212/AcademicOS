## What v0.2 actually established

LifeHub has crossed from a pluginized dashboard prototype to an extension-kernel prototype.

Useful properties to preserve:

1. Plugins are packages of contributions rather than a closed kind taxonomy.
2. Extension points are arbitrary identifiers; Core does not own a final allowlist.
3. Cross-plugin storage reads require both a manifest request and a local grant.
4. Those grants can be revoked.
5. Workspace state stores generic extension references rather than domain-specific objects.
6. The current web board is only one consumer of workspace.widget.
7. Outbound retrieval remains host-mediated.
8. Arbitrary third-party executable Python is deliberately not treated as a safe plugin runtime.

## What is still missing

Do not describe the repository as a finished open plugin platform. Missing work includes secure package installation, an executable third-party sandbox, lifecycle supervision, versioned service contracts, sandboxed custom UI, package trust/update infrastructure, formal information-flow enforcement, formal provenance semantics, person-scoped authority semantics, and any verified IR/compiler.

The existing host API boundary is not an operating-system sandbox.

## Product/platform thesis

> LifeHub does not define your digital life. It provides the mechanisms by which you assemble it.

The kernel should own mechanisms: package identity, registry, capability routing, storage, runtime/lifecycle, provenance, network/effect mediation, and policy enforcement.

The kernel should not own life-domain concepts such as course, workout, stock, restaurant, trip, robot, or habit.

Semantic contracts belong to the ecosystem and should be independently versioned.

## Plugin ingress

Plugin ingress is broader than manifest parsing. Keep four planes distinct:

1. Discovery/description — identity, version, contributions, requested capabilities.
2. Binding/control — interface resolution, grants, activation, lifecycle.
3. Data plane — observations, messages, records, streams, requests/responses.
4. Execution plane — the sandbox/runtime for untrusted code.

Preferred high-level sequence:

~~~text
Package -> Declare -> Resolve -> Grant -> Activate
                                  |
                                  v
Plugin Runtime <---- mediated protocol ----> LifeHub
~~~

Keep extension points, semantic interfaces, capabilities, and events separate. Do not let plugins directly import each other's implementation or share unrestricted database access.

## External information boundary

Preferred shape:

~~~text
External site/API/file/device
        |
        v
Connector / Adapter
        |
        v
Typed Observation / internal contract
        |
        v
Local computation / composition
~~~

The goal for websites is not stealth scraping or bypassing anti-bot systems. Prefer official APIs and permitted retrieval. Centralize retrieval policy, caching, conditional requests, credentials, rate limits, retry/backoff, audit, and revocation.

## Research hypothesis: Person-Oriented Programming

Person-Oriented Programming (POP) is a working research label, not an established novelty claim.

Research question:

> What would programming look like if the persistent unit of state, authority, provenance, and accountability were a person-associated digital domain rather than the application?

Do not model the human being as a software object. Use a PersonalDomain<P>-style abstraction for the persistent digital computational domain associated with person P.

Candidate separation:

~~~text
Observation -> Derivation -> Proposal -> Authority Check -> Commit
~~~

External effects remain separate:

~~~text
Computation -> EffectRequest -> Authority / Delegation -> Effect Executor -> External World
~~~

Candidate invariant:

> Program computation does not itself imply authority to mutate durable personal state or the external world.

Authority may be delegated by prior policy and later revoked.

## Egress correction

An absolute rule such as “personal data can never leave the machine” is unusable. Email, assignment submission, collaboration, purchases, and intentional AI use require legitimate egress.

Better candidate invariant:

> Personal data must not silently egress. Egress requires an explicit, scoped authority/declassification path.

Treat declassification/authorized disclosure as first-class. Scope every security claim to a threat model; a capability graph does not prove absence of all covert channels.

## Evidence and authority

Preserve:

~~~text
Evidence / Observation
        ->
Interpretation / Derived state
        ->
Suggestion / Proposal
        ->
Authority / Commit
~~~

Rejecting a proposal does not rewrite an observation. Accepting a proposal does not turn an inference into evidence. AI should normally produce interpretations/proposals, not manufacture authority.

## Why a new IR is being considered

The goal is not new syntax. The hypothesis is that a new IR/runtime could make authority, provenance, information flow, proposals, commits, and effects part of program semantics rather than application conventions.

Candidate model:

~~~text
Program_P :
    (AuthorizedView_P, Inputs, Capabilities)
      -> (Derived, Proposal, EffectRequest)

Commit(State_P, Proposal, Authority_P) -> State'_P

Authorize(EffectRequest, DelegatedAuthority_P) -> Effect
~~~

Programs should not receive arbitrary ambient filesystem/network/process authority.

## Falsification strategy

Implement a representative extension twice:

- baseline: WASM Component/WIT or another conventional capability-limited component runtime
- experiment: PersonIR + verifier + runtime

Compare authority, delegation/revocation, durable state ownership, provenance, information-flow control, proposal/commit, effect control, auditability, debugging, developer complexity, performance, and openness.

If PersonIR is merely a more cumbersome spelling of a conventional capability host, remove it and keep the useful ideas in the ordinary LifeHub runtime.

## Required heterogeneous scenarios

At minimum test:

1. academic planning — observations and reversible local proposals
2. email/message sending — irreversible external effect
3. payment/purchase — high-authority effect and stale-state risk
4. smart-home/device action — physical-world effect and timing
5. collaboration/shared state — authority is not owned by one person alone

Any model that only works elegantly for calendar/task planning is not general enough.

## Hard problems not to hide behind syntax

- TOCTOU and stale proposals
- idempotency under incremental recomputation
- irreversible external effects
- multi-person authority/shared state
- legitimate egress and declassification
- provenance propagation
- nondeterministic time/random/network/AI inputs
- covert channels and verifier/runtime bugs
- connector/driver escape hatches
- source/IR/verifier versioning
- explainability/debugging
- avoiding a universal kernel ontology

## Prior-art discipline

Do not market local-first data, capability security, sandboxing, personal data stores, manifests, event sourcing, provenance, effect systems, information-flow control, WASM/WASI, signed packages, extension points, or dashboards as LifeHub inventions.

The possible contribution is a particular composition around person-associated durable state, delegated authority, provenance, proposal/commit, explicit effects, and open extensions. That remains a hypothesis.

A deep-research pass was initiated around this question. Unless its final report is explicitly added to the repository, do not assume that it produced a citable final result.

## Immediate next milestone

Not “invent the LifeHub language.”

Instead:

> Demonstrate or falsify a minimal PersonIR in which person-associated state, authority, provenance, information flow, proposals/commits, and effects are enforceable semantics rather than application conventions.

Expected deliverables:

1. computational model
2. tiny IR
3. verifier
4. interpreter/runtime
5. heterogeneous examples
6. hostile-extension tests
7. conventional capability-runtime baseline
8. written failure criteria

Failure of POP/PersonIR does not imply failure of LifeHub. Preserve useful capability/provenance/effect lessons even if the language experiment is abandoned.

## Working rule

Prefer falsifiable invariants over names, diagrams, and “paradigm” language.

For each abstraction ask:

1. What concrete program becomes safer or simpler?
2. What can the verifier prove?
3. What still requires runtime enforcement?
4. What cannot be guaranteed under the threat model?
5. Can a conventional capability runtime express the same thing with similar clarity?
6. Which heterogeneous scenario breaks it?
