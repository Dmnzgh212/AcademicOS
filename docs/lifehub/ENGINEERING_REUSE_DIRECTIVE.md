# LifeHub 最高工程指示补充决议：复用优先、适配驱动、大小模块分别处理

**决议编号：LH-D-REUSE-001**  
**日期：2026-10-07（北美东部时间）**  
**性质：项目方明确确认的工程执行原则，作为《LifeHub 核心理念与最高工程指导》的补充。**  
**状态：已提交文档 PR #62，待审阅合并；不等于已进入 main，不等于 M1 验收。**

## 一、问题裁决

针对近期 PR #63（机制文献/标准综合）与 PR #64（封闭 Python 操作模型）的分歧，结论如下：

1. **研究方向可以保留，不判定既有成果无效。** 调查 WIT、UCAN、Cedar、W3C PROV、Jif 等先例，以及用一个小模型检验普通 API 和操作图是否存在差异，是合理的前期工作；第零阶段的结论只是封闭模型结果，**不代表已真实复用上游实现**，不构成 PersonIR 优势证据。
2. **纠正工程推进方式：发现成熟机制后，不能默认自己再实现一套。** 真正目标是先找到可维护、可授权使用的现成实现，**先接入或摘取可用模块做真实适配测试**；哪里不满足 LifeHub 的具体要求，再有针对性地修改接口、补充一层适配器或局部修复。
3. **大模块复用，小模块按效率自己写。** 不应为了“全部复用”而引入比任务本身更重的依赖。边界清楚、简单且有单元验证的小工具、胶水代码、解析/转换函数可以直接编写。不能因为工作量小，就要求先做冗长的选型报告。
4. **严禁为了原创而重造基础设施，也严禁不加甄别直接复制。** 复用必须满足实际许可、安全、维护及平台约束；此原则服务于产品交付，不是为依赖数量、研究文章或 PR 数量设置指标。
5. **本决议不改变 LifeHub 根本方向。** “Software proposes. The Person commits.” 所代表的个人主权、可委托可撤销权限、Engine 独立于 Shell、第三方应用无需修改 Core 才能接入等原则均保持不变。

## 二、最高工程执行顺序

**对大型成熟能力，默认流程必须是：**

```text
确定当前真实问题 / 需要满足的验收行为
  → 搜索仓库已有模块、维护中的成熟开源实现与标准库
  → 比较 1–3 个实际可落地候选的许可证、维护、安全、平台和接口适配性
  → 选择最小、最稳、最易升级的复用路径
  → 首先在隔离环境中接入原版依赖/提取模块，跑真实端到端适配测试
  → 记录真实不兼容处、具体错误和边界缺口
  → 优先写薄适配层或提交上游修复 / 局部补丁
  → 只有无法合理适配、许可证不合适、维护中断或成本/风险更高时才自行重写
  → 将有效实现接入产品的公开组件契约，保留可复现实验证据
```

**所谓“先拿来用”，优先级是：**

- **A. 直接使用成熟依赖/系统 API**，通过常规包管理或系统调用固定版本；优先获取上游安全维护和更新。
- **B. 通过薄 Adapter / wrapper 适配 LifeHub**，尽量不修改上游，保留替换自由。
- **C. 摘取/复制局部实现或维护一个小 fork**，仅在许可允许、归属和通知义务明确、适配边界小、并有可跟进的更新/安全责任时采用。
- **D. 独立实现**，仅在 A–C 不可行或者小型模块独立编写确实更简单、可靠、经济时采用。

**不是任何项目只要叫“标准”就有可直接复用的运行时代码。** WIT、UCAN、PROV 与 Jif 有不同成熟度、职责和语言/宿主约束；研究它们不等于必须同时引入，也不能把接口标准误当成授权执行器。要复用的是一个**能安装、能运行、能测、能维护的具体实现**，而不只是其概念。

## 三、大模块与小模块的界线

不以代码行数粗暴判定，而以**技术复杂度、跨平台负担、安全责任、依赖维护成本和复用收益**判定：

| 工作种类 | 默认取舍 | 可接受的交付证据 |
| --- | --- | --- |
| Wasm 执行、数据库、进程资源限制、成熟授权引擎、RPC/网络协议、密码学、标准序列化、可维护 SDK 基础设施 | **优先复用成熟库或系统 API** | 固定版本、许可证及边界、可运行适配测试、回退方案 |
| 组件公开协议/宿主能力映射、权限生命周期绑定、审计与可撤销授权适配 | **复用基础设施 + LifeHub 薄适配层** | 实际包安装/运行/撤销和安全回归 |
| 简短转换函数、固定小工具、特定样例、胶水代码、局部测试辅助 | **可直接自行编写** | 易懂的实现与针对性测试；无无谓依赖 |
| 个人主权/数据披露/多主体授权等成熟工具不能覆盖的真实需求 | **先验证差距，再有界原创** | 真实反例、与成熟方案公平对比、可证伪结果 |

举例：若要集成授权判断，应**先实际运行**一个合适的成熟授权库或保持并验证现有宿主策略机制，而不是先按 Cedar 的文章新写一套 policy engine；但也不应因为 Cedar 理论上适合，就在没有需求、性能/语言适配或迁移证据时引入生产 Core。

## 四、适配验证的最低要求

当团队决定复用一个大型模块时，尽量交付以下可核验产物，而不只是“看过资料”：

1. **需求和边界**：解决哪个真实行为缺口（例如后台资源限制、授权撤销、组件版本化），不扩大成泛泛的“建设完整系统”。
2. **上游选择**：具体仓库/库名、版本/提交、许可证、维护现状、安全或供应链风险、为何优于自己实现。
3. **最小适配实验**：不靠 Mock 冒充真实运行，运行原版组件 + 最薄的 LifeHub Adapter；证明输入、输出、失败、资源和授权边界。
4. **差距清单**：哪里适配不上、改动了什么、为什么要改；先改接口/配置再考虑侵入式 Fork 或替换。
5. **可回退**：尽量把第三方实现放在可替换边界后，避免单一库锁定 LifeHub Core、Shell 或人的数据。
6. **真实交付**：应用包可安装、受管运行、通信、撤销和恢复（只列出与该模块有关的验收行为）；保留 Windows/Linux 等适用平台的运行证据。

一次小型修复不需要提交六章论文；**上面的记录可以是一段精简 PR 说明及验证输出**。安全关键依赖才需要更全面的审查。

## 五、研究与工程分工裁决

- **PR #63：保留为先例/适配候选研究**，尚不能计作可直接复用的依赖落地。
- **PR #64：保留为小型封闭语义实验**；这类代码可自行写，现阶段证据表明共享宿主检查而非操作图带来关键约束，不能宣称 PersonIR 独有安全优势。
- **下一步若继续 PersonIR 研究**：选出一个真正存在的、可安装的成熟方案与具体接口（而不是同时造五种基础设施），在隔离实验中先完成“原版接入 + 小适配 + 对比测试”。允许得出“普通宿主足够，暂不需要 PersonIR”的否定结论。
- **生产 Engine 主线**：继续依照 M1 验收要求完成可用第三方后台软件与真实跨平台证明；**不因研究 PR #63/#64 而暂停 M1，也不强迫当下引入 Cedar/UCAN/PROV/WIT**。
- **报告频率**：常规工作不要求逐 PR 复审；重大授权/数据损坏/架构冲突及时报告，M1 节点集中验收。

## 六、不可误读的约束

- “先搜”不是无限期看论文；“先用”不是不检查就粘贴整个仓库。
- “复制”必须履行许可证、版权通知、归属、依赖及安全修复义务；受许可约束较重的实现不能靠删版权标记绕开限制。
- 不因为现成代码恰好存在就牺牲个人主权、最小授权、用户可撤销性或 Shell 替换性。
- 不把大模块拆成多个“小模块”来合理化重新发明通用执行器/权限引擎。
- 不把几百行小程序、一轮模型检查或 CI 绿灯宣称为完整生态或 PersonIR 已被证明。
- **性能和效率需实测，不设虚构的“80% 复用率”等数字指标。**

> **最高执行口径：先找现成的，先拿来做适配测试；哪里有问题改哪里。复杂大模块优先复用成熟实现；简单小模块按效率自己写。只有真实缺口才值得原创。**
