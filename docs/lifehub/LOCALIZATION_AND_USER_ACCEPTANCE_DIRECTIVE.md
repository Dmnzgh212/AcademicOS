## 一、核心解释（以本决议为准）

LifeHub 是**个人掌握控制权的开放式数字计算平台**。开放指**可吸收不同来源的成熟技术、可按需扩展功能、采用统一的可替换内部契约**，不等于为任意外部二进制或在线服务开放无限制直通接口，也不以第三方插件商店/外部开发者生态为第一阶段目标。

对课程、邮件、日程、信息处理等产品能力，项目优先从成熟开源项目中寻找有用代码，**在许可证允许下选择性复制/摘取到本地，审查、裁剪、改造、统一接口与权限，再作为 LifeHub 自己维护的本地模块使用**。不是仅仅给远程服务一个 token，或让上游插件照原样获得内部读写权限。

本地化不是重命名与换 UI：须实际消除不必要的依赖和多余权限、适配平台协议与离线/本地数据边界、测试运行，并能替换或移除。

重要区分：
- **应用/业务功能源码：** 优先筛选、合法复制所需部分并本地改造。也可以按适配成本把上游作为受控、固定版本的本地依赖；不得把所有第三方代码强制复制进 Core。
- **复杂底层基础设施（Wasm VM、数据库、加密、成熟解析/序列化和系统进程机制）：** 不因“复制优先”而手抄重写；优先保留维护中的标准库、系统 API 或本地固定依赖，必要时按许可证做小范围 vendor/fork，以安全、升级和维护成本决定。
- **小功能/胶水代码：** 自行编写通常更快，不要求无意义的开源选型仪式。
- **外部服务/API：** 仅在功能确实需要并得到个人授权时经过受控连接器使用；不是默认平台内部能力。
- **可独立打包的软件：** 可以由项目内部开发人员、AI 工程助手或外部贡献者制作；“独立模块”说的是**独立于 Engine Core 的安装/运行和权限边界**，不是必须由外部人类编写。

“Software proposes. Authority commits. The Person is the root of authority.” 不变。人可以签发有限、可撤销的持续授权；自动任务不必每次要求用户手动批准，但不能越权。

## 二、项目默认工作流：选、复制、改、验、收

1. **确认具体需求与最小功能面。** 先问“这次要一个什么能力”，不是“能否支持所有插件类型”。
2. **查现有实现。** 优先看仓库已有代码和维护中的开源项目；记录来源、版本、许可证、维护状态和安全历史，避免无目标的论文堆积。
3. **评估合法移植范围。** 识别源码许可证及传播、署名、修改说明、开源义务；分析是否与未来分发模式兼容。不能默认所有 GitHub 代码都可复制，也不能删除版权标记。
4. **挑必要部分复制到受控本地模块。** 对复杂、紧密耦合/许可敏感的实现，可以采用固定版本依赖或隔离 Adapter；这不违反“本地化优先”，前提是**不暴露上游的过宽权限和不受控更新**。
5. **裁剪与协议适配。** 统一输入/输出、数据模式、错误处理、版本和 LifeHub 授权；业务逻辑不写死在 Core。优先局部修改，不把上游整个项目绑成不可替换黑盒。
6. **实测与安全验证。** 使用模拟数据先验证，审查来源与依赖、权限清单、沙箱/进程隔离、输入限制、数据访问与网络外发、凭证管理、撤销、卸载、故障、回滚和跨平台相关边界。高风险能力增加专项审查；不能因“本地复制”就宣称安全。
7. **交付用户可操作的安装/导入/运行方式。** 代码、适配器、构建脚本、自动测试、简明操作文档和报错收集方式由工程团队提供；用户不需要学编译 Wasm、开发 SDK 或理解整个权限模型。
8. **保留更新路径。** 上游版本与移植 commit、许可证 NOTICE、已更改模块、差异补丁、安全修复同步责任和替换方案需可追溯；复制不是一次性永久安全。

决策记录尽量精简：`上游来源/版本与许可证 → 使用的子模块 → 本地修改 → 需求满足情况 → 安全/运行测试 → 残留风险`。不是每个小函数都要一篇报告。

## 三、两条不同的验证责任线

### A. 工程与安全验证——开发者 / AI 工程助手负责（必须）

- 真实构建并运行，优先使用已安装软件包而非只在源码目录跑；
- 软件独立于 Core；受控接口、最小授权、不可信内容边界、可撤销权限；
- 安装、运行、数据交换、停用、卸载、崩溃和恢复按该模块实际相关的能力测试；
- Windows/Linux 等**适用目标平台**验证；结构化日志、故障证据和可复现步骤；
- 依赖/移植代码的许可、来源、安全、更新、敏感信息泄露检查；
- 不将 CI 绿灯、形式完整的日志或“由另一 Agent 撰写”冒称真实独立人类安全审计。

安全风险没有审清可以拒绝交付，**但不能把审查与调试任务转嫁给普通用户**。

### B. 用户可用性验证——普通用户只做轻量操作（低门槛）

不要求用户懂 Python、Wasm、WAT、SDK、Engine 内部结构、Git 分支或开发插件。最小目标：

1. 按一个明确入口**导入/安装**经工程验证的模块；
2. **启动/运行**并看到一个能理解的结果；
3. 查看并**确认或拒绝**具体权限请求，能够停用、撤销和卸载；
4. 发生问题时**复制错误提示/导出脱敏诊断包**交给工程人员处理；
5. 可选做一次**安全感知**检查：确认功能没有申请不相关权限，数据共享有明确说明；不要求亲自渗透测试、核查源码或验证密码学。

**用户不必贡献源码；不必找另一位程序员；不必制作 provider/consumer 才能验收基本可用性。**
用户参与操作可延期于具备易用安装界面/CLI 后，不作为 **M1 引擎技术验收**的外部人类作者硬门槛。

## 四、M1 门槛重新厘定

M1 证明的是**受控本地独立模块可被 Engine 真实运行、监管、授权和恢复**，不是证明第三方开发者生态成熟。

M1 保留的硬性工程证据：
- 两个**可分别打包的非 Core Wasm 模块**，通过公开受控契约通信；作者可相同，AI 工程助手可参与；
- 关闭 Shell 后后台 guest 自行持续工作，而不是只证明 daemon 存活；
- 权限授权、撤销、过期/重装失效；
- 实际 guest / Engine 进程故障后的有界自动恢复、正确停止与卸载清理；
- 真实 Windows/Linux 已安装产物验证、可复现日志/包身份；
- 资源隔离与安全边界保持明确：未实现的 CPU/内存聚合上限、卡死检测等不能伪称已经解决，且需评估是否存在阻止 Alpha 交付的风险；
- 单独的工程代码审查/集成审查和显式验收批准。

**从 M1 必选门槛移出：** 必须找到与 Engine 作者无关的**外部人类程序员**，独立从零制作插件并提交两份源码。可保留为以后 SDK/开发生态阶段的*可选或单独定义的*验证，不得卡住当前技术 Alpha。

现有 [PR #65](https://github.com/Dmnzgh212/AcademicOS/pull/65) 的 AI 独立接入、[CI #384](https://github.com/Dmnzgh212/AcademicOS/actions/runs/37730269391) 可作为**不同业务应用的工程验证**，如实标注 AI 作者，不需冒充人类。原 M1 未通过/尚未合并的事实不会因决议自动改写。

**此条为项目方要求的验收范围修订**，须同步更新 [M1 验收 PR #56](https://github.com/Dmnzgh212/AcademicOS/pull/56) 和工程审计文档，在审查后再宣布新的 M1 结论。

## 五、项目近期安排与红线

- **短期：** 根据新 M1 标准集中审查现有后台工作、归档证据、提出必要修补；不要继续强制搜寻外部程序员；不要等一名不会写 Wasm 的普通用户来填安全验收表。
- **随后：** 选择一个实际有用的开源功能模块，从许可证允许的部分复制并本地化，做一份用户能导入、运行、撤销、复制报错的最小交付。选择任务/日程等用途时保持业务逻辑在模块内，不改变 Core 的通用性质。
- **保留开放性：** 外部贡献、公开扩展协议和经过审查的独立包仍可支持，但不能自动取得权限；“开放”不意味着所有外部代码都应被允许运行。
- **延续研究隔离：** PersonIR 的语义研究继续与生产独立，未证明必要性不得开发新编译器来替代成熟机制。

**不予授权：** 关闭权限校验、跳过安全审查、违反版权许可、默认复制完整上游仓库、将用户变成安全测试员、擅自合并所有 Draft、把 M1 技术完成等同于 LifeHub 完成。

> **最高执行口径：先从优秀开源中拿到真正有用的代码，合法复制、裁剪、改造成本地能力；复杂底层依赖以安全和维护为先。由工程团队把模块做好、验证好，交给用户的是会导入、会运行、会撤销、会反馈错误的简单产品，而不是一套开发者考试。**
